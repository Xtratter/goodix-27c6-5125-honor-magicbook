# Технический долг и открытые вопросы

Состояние на 2026-10-09. Пункты упорядочены по тому, насколько мешают в повседневной работе.

## 1. Внезапные перезагрузки ноутбука (HONOR BMH-WDX9)

Ноутбук несколько раз жёстко перезагружался на батарее, всегда сразу после всплеска нагрузки на все ядра; журнал обрывается без ошибки, `pstore` пуст,
событий кнопки питания нет. Причина **не доказана**. Что известно: четыре сброса (два при компиляции на 16 потоках, два при лёгкой работе); журнал
телеметрии (`crash-telemetry`, строка каждые 2 с) показывает рост нагрузки за несколько секунд до последнего; запуски на двух ядрах не вызывали сброса.
После подключения зарядки ноутбук работал больше часа без сброса (это не доказательство).

Что сделать отдельно: несколько часов поработать от зарядного устройства; запускать `crash-telemetry` автоматически (служба пользователя); проверить
состояние батареи (около 89 % проектной ёмкости, 132 цикла) и наличие обновления BIOS/EC (BIOS 1.15 от января 2024); если на зарядке сбросы
продолжатся, подозревать железо.

## 2. Установленный драйвер в повседневной работе

Три патча (повтор слабых кадров, порог покрытия 85 %, ранний ответ) проверены юнит-тестами и запусками `fprintd-verify`, но ещё не на всех реальных
путях (экран блокировки, `sudo`, выход из сна): итог живой проверки смотрите в заметках ниже. После патча раннего ответа выросло число запросов
повтора (все из-за пустых кадров); сравнение двух версий пакета одной и той же техникой покажет, виноват ли патч.

## 2b. Экран блокировки поздно запускает проверку отпечатка (KDE, не драйвер)

Plasma 6.7.4 запускает проверку отпечатка только когда показан интерфейс экрана блокировки (клавиша, щелчок, движение мыши), по журналам через 8-12 с после
блокировки. Быстрые касания к тому же дают пустые кадры. Описано в `install.md`. Возможное исправление, **не сделано**, потому что правит критичный для
безопасности экран блокировки и перезатирается обновлениями: копия темы экрана блокировки с одним дополнительным вызовом
`authenticator.startAuthenticating()`, сначала проверить через `kscreenlocker_greet --testing`. Кадр после ожидания полного контакта пальца рассматривался и
**отвергнут по данным**: среди собранных быстрых касаний не было ни одного с пустым первым и хорошим более поздним кадром.

**Эксперимент (2026-10-09), итог: заставить экран блокировки запускать проверку самому не удалось.** Копия экрана блокировки на уровне пользователя
(`kscreenlocker_greet --testing --shell local.fptest`, системные файлы не тронуты) с дополнительным вызовом `authenticator.startAuthenticating()`, сначала
при создании, затем через 600 мс, **не** запустила fprintd до первого касания (блокировка в 14:25:44, fprintd в 14:25:54; блокировка в 14:26:54, fprintd в
14:27:15), то есть одного вызова недостаточно, и пришлось бы разбирать внутренности greeter'а. Копия удалена.
**Вероятная причина потерянного первого касания:** сканер — это кнопка питания, поэтому само касание будит экран блокировки; проверка запускается, пока палец ещё
лежит на сканере, и инициализация драйвера отказывается калибровать при пальце на нём (`Finger contact changed during Goodix calibration; remove the finger`),
после чего экран блокировки перезапускает проверку. Возможные исправления в драйвере, не сделаны: ждать снятия пальца вместо ошибки или использовать
кэшированный базовый кадр без пальца, чтобы лежащий палец не мешал (оба меняют записанные тесты устройства).

## 3. Сопряжение с Windows

В сканер записан новый случайный PSK, поэтому Windows-драйвер больше не совпадает с сохранённым им ключом. Возможно, Windows Hello потребуется записать
палец заново, а Linux потом придётся заново сопрягать; не проверялось. Файл `/var/lib/fprint/goodix5125/psk` удалять нельзя (старый ключ не
восстановить).

## 4. Проект своего матчера (остановлен после этапа 1)

Кандидат B (BLPOC) проиграл `openchicago`; проект остановлен решением. Чтобы продолжить: собрать новые аккуратно размеченные данные (один палец на
запуск), сделать прототип кандидата C, снять недостающую сессию `natural-2`. Открытые мелочи итогового ревью: список исключений не под версионным
контролем, а опечатка в нём молча игнорируется; замок отложенных пишется до оценки, не имеет пути по умолчанию и хеша ключей отложенных; обёртка не
проверяет `malloc`, не отвергает `n_frames <= 0` и не потокобезопасна; оценки адаптивного сеанса `openchicago` могут зависеть от порядка проб; сборщик
работает от root с кодом, доступным пользователю для записи (описано); `load_dataset` загружает любой `*.npz` под корнем.
