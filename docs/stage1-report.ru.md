# Свой матчер, отчёт этапа 1 (M0-M2)

Этап 1 [дизайна](superpowers/specs/2026-10-09-goodix5125-clean-matcher-design.md), выполненный по
[плану](superpowers/plans/2026-10-09-goodix5125-matcher-stage1.md). Здесь только агрегированные числа: кадры касаний — биометрические данные и
остаются на машине владельца. Лаборатория — локальный репозиторий, не опубликован.

## Вердикт

**Кандидат B (фазовая корреляция в ограниченной полосе с шаблоном из нескольких фрагментов) не проходит критерий успеха**: он не дотягивает до
текущего матчера `openchicago`. Владелец подтвердил, что при сборе были касания не теми пальцами, чем спорное чужое касание окончательно
признано записанным пальцем.

Протокол `varied -> natural-1`, разработческая часть, одна эффективная складка, **12 различных своих** и **17-21 различных чужих** касаний:

| Матчер | касание исключено: FRR@FAR0 / зазор | касание оставлено: FRR@FAR0 / зазор | время на оценку |
|---|---|---|---|
| `openchicago` (текущий) | **0,0% / +28** | **100% / -39** | 11 мс |
| SIFT с парными проверками (приближение SIGFM) | 25,0% / -2,0 | 25,0% / -2,0 | 3 мс |
| BLPOC, лучший из 36 настроенных вариантов | 25,0% / -2,0 | 25,0% / -2,0 | 64 мс |

Спорное касание (первое касание запуска левого указательного) даёт у `openchicago` 54 по шаблону `varied` и 71 / 67 по шаблонам из других касаний, как
записанный палец, тогда как остальные чужие дают не больше 0. Доказательство получено от самого `openchicago`, поэтому исключение касания работает в его
пользу; обе трактовки показаны выше с одинаковым весом. Ни у одного варианта BLPOC нет положительного зазора. Если считать пустые (отклонённые) кадры
своих отказами, FRR составляет 52% у `openchicago` и 64% у двух других.

## Что построено

Лаборатория на Python (загрузка набора, протоколы, стабильное разбиение «разработка / отложенные» по хешу касания с защитой, метрики с бутстрепом по
различным касаниям, интерфейс матчера, раннер оценки, ctypes-обёртка над `openchicago` (только публичный заголовок), обёртка для сборщика автора
драйвера, прототип BLPOC, настройка с записью всех кандидатов, статистика гребней). 108 тестов.

## Чему научили данные

- Около половины быстрых «обычных» касаний не содержат пальца ни в одном снятом кадре: драйвер тоже видит много пустых кадров и просит повторить.
  Поэтому «обычные» группы считаются в полезных касаниях, пустые кадры — это повторы, а не ошибки.
- Сборщик читает кадры после события касания; у быстрых касаний палец есть только в первом кадре, поэтому по умолчанию берётся он.
- Сборщик автора подключается с нулевым PSK, а у этого сканера случайный, поэтому обёртка подставляет ключ на лету (читается от root, нигде не копируется).
- Период гребней 10,7 пикселя (0,094 цикл/пиксель) во всех группах.

## Итоговая проверка изменила результаты

Независимая проверка показала, что первое разбиение зависело от размера группы (исключение одного касания перетасовало большую часть отложенных), а
критерий настройки (нормированный зазор) мог выбирать явно худшего кандидата. Теперь разбиение — стабильный хеш ключа самого касания, а выбор идёт по
FRR, затем по зазору. Все числа первых черновиков (в том числе «ни один вариант BLPOC не разделяет пальцы, лучший FRR 100%») пересчитаны: лучший BLPOC
даёт 25%. Отложенные данные (5 полезных чужих, 4 полезных natural-1 и 3 varied) ни разу не использовались для решения, но многие из их касаний в
черновиках входили в разработческую часть и оценивались базовыми линиями; для чистой итоговой проверки следующего кандидата нужны свежие данные (и
недостающая сессия `natural-2`).

## Ограничения

Один человек, один записанный палец, один сканер, одна сессия «обычных» касаний. 12 своих проб дают разрешение FRR около 8%; около 20 чужих не показывают
FAR ниже примерно 15%. Сеанс `openchicago` адаптивный, пробы оценивались в фиксированном порядке. `natural-2` не снималась. Ноутбук несколько раз
перезагружался на батарее сразу после всплесков нагрузки на все ядра (причина не доказана), поэтому лаборатория ограничивает любые вычисления двумя потоками
и двумя ядрами.

## Решение

Путь дизайна по умолчанию после неудачного M2 — кандидат C. Выбор был делегирован владельцем, и принято решение **остановиться на этом**:
`openchicago` с тремя опубликованными патчами разделяет эти данные идеально (0% FRR@FAR0, зазор +28), набор слишком мал, а его метки слишком
ненадёжны для честной новой проверки, и остающаяся причина заменять `openchicago` — происхождение его кода, а не точность.

Чтобы продолжить: собрать новые данные по проверенному протоколу (один палец на запуск, подтверждённые метки), затем сделать прототип
кандидата C в той же лаборатории и решить на нетронутых отложенных данных плюс недостающей сессии `natural-2`. Все принятые решения лежат в
`docs/execution-ledger.md` лаборатории.
